## What this runbook is for

A maintenance **sweep** runs the `audit-*` lenses full-scope, dedups their
findings against the Issues earlier sweeps filed, and turns what is genuinely
new into Stories. It is the unattended sibling of an interactive `/audit-to-stories`
run: no HITL gates, so every judgement call the interactive path asks a human
has to be settled here instead.

| Setting | Value for this repository |
| --- | --- |
| Cadence | _e.g. weekly, Sunday 02:00_ |
| Lenses in scope | _e.g. security, clean-code, quality, dependencies_ |
| Severity floor | _`--severity`, default `high`_ |
| Story filer | _e.g. the scheduled job, or @your-handle_ |
| Story triage owner | _e.g. the on-call maintainer_ |

## Step 1 — Run the lenses full-scope

Run each `audit-*` workflow with **no** `--paths` and no change-set filter, so
the whole target-set union is audited rather than whatever a recent branch
happened to touch. Each lens writes its report to
`temp/audits/audit-<lens>-results.md`.

A sweep scoped to a change set is not a sweep: it re-reports the same recent
files every cycle and never reaches the code nobody has touched in a year,
which is exactly where audit findings accumulate.

## Step 2 — Cross-check the severity tally

Every lens report ends its executive summary with a machine-readable line:

```text
Severity tally: Critical 0 / High 3 / Medium 7 / Low 2
```

The CLI re-counts the `### Finding` blocks it actually parsed and compares them
to that declared tally. A mismatch — or a missing tally line — means the report
is not trustworthy: a finding was malformed, a severity did not resolve onto the
canonical scale, or the lens truncated its own output.

The line is read **from the Executive Summary**, and a report declaring it more
than once fails as `duplicate-tally` naming both lines rather than adopting
whichever the scan reached first. Prose elsewhere in the report that quotes the
tally format is a second declaration as far as the check is concerned; move it
or reword it.

A `###` heading with no severity axis and no field bullets is read as a
**grouping header**, not as a finding — so a lens that emits `### Robust` with
`_No findings._` under it contributes zero findings and still cross-checks
against a zero tally.

`--auto` **fails closed** on any such failure. It exits non-zero having opened
no Issue, and names the offending report in
`summary.reportFailures[]`. `--allow-missing-tally` is a `--scan` affordance
only; `--auto` ignores it by design, because an unattended run has no operator
to read a warning.

**When the sweep goes red here, re-run the lens.** Do not reach for
`--allow-missing-tally` and do not hand-edit the report to make the numbers
agree — the tally is the only signal that the parse saw what the lens wrote.

## Step 3 — Dry-run the first cycles

Start every new sweep in report-only mode, and stay there until the tallies
stop surprising you:

```bash
node .agents/scripts/audit-to-stories.js --auto --dry-run
```

`--severity` is validated against the canonical scale: a typo (`--severity Hgh`)
exits non-zero naming the accepted levels rather than silently widening the run
to every finding.

`--dry-run` performs zero GitHub writes, printing only the run summary. Read `totals.create` before you let the sweep file
anything: a first full-scope run over an un-audited repository can propose more
Stories than your team can triage in a quarter. Raise `--severity` until the
create count is a batch you would actually take on, then go live.

## Step 4 — Go live: file and wire

```bash
node .agents/scripts/audit-to-stories.js --auto
```

`--auto` writes nothing itself — no file, no branch, no PR. It prints the run
summary, including `createGroupKeys`: the groups nothing already filed covers.
File those as Issues (the `--emit-stories` payloads, each carrying its
`audit-fingerprints` / `audit-semantic-keys` footers), then replay the opened
numbers through `--wire-edges` (Step 5).

**The Issues are the sweep's memory.** There is no ledger to commit: the
provenance footers each filed Story carries are what the next sweep matches
findings against, read from live GitHub state. An **open** Issue with a
matching footer classifies the finding `skip-open`; a **closed** one —
completed or `not_planned` — classifies it `skip-reoccurring`, skipped by
default and surfaced in the summary for review; a finding reworded at an
unmoved location still matches on its semantic key. So an ephemeral checkout
loses nothing when it is thrown away, and to reject a finding for good, close
its Issue as `not_planned`.

Never strip or hand-edit a Story's `audit-*` footers: removing one is how a
finding gets re-proposed.

## Step 5 — Enrich before you deliver

`--emit-stories` renders `{ title, body, labels }` payloads from audit findings.
Those bodies are **audit prose**, not delivery-ready Specs: they describe a
symptom and a recommendation, not a scoped change with acceptance criteria a
worker can verify against.

Do not point `/mandrel-deliver` at a freshly-filed audit Story — and as of the
label guard below, you cannot: `resolve-stories.js` refuses a Story carrying no
`agent::*` label, naming this step, unless `--allow-unlabelled` is passed. Route
it through `/mandrel-plan` first — the planning pass is where the finding becomes a
capability slice with a `## Spec`, real `acceptance[]` items and runnable
`verify[]` lines. Planning is deliberately not automated here: deciding what a
finding is worth, and how far the fix should reach, is the judgement the sweep
exists to surface rather than to make.

The wiring pass is the exception — it _is_ mechanical and it is **required**.
After opening the Issues, replay their numbers through `--wire-edges` so the
cohort's declared ordering exists as `blocked by #N` footers and native
`blocked_by` relations. An unwired cohort is genuinely unordered, and
`/mandrel-deliver` will co-dispatch Stories the edges say must follow one
another.

## Step 6 — Label convention

Audit-sourced Stories carry a closed label set, so they can be filtered out of
(or into) ordinary planning at a glance:

| Label | Meaning |
| --- | --- |
| `type::story` | Every emitted Story — the sweep never opens Epics or tasks. |
| `audit::<lens>` | One per lens represented in the group; a cross-audit merge carries several. |
| `risk::high` | Added when any finding in the group is Critical. |

**There is no `agent::` state label in that set, and that is the point.** The
sweep files a Story it has deliberately not made deliverable — Step 5 above is
the reason. `agent::ready` is what `/mandrel-deliver` reads as "available for
pickup", so a sweep that applied it would route unenriched audit prose straight
into delivery, which is the outcome Step 5 tells you to avoid. The label is
applied by `/mandrel-plan`, at the end of planning, once the finding is a
scoped slice. If you file these Issues by hand, apply the emitted `labels[]`
verbatim and do not top it up with a state.

The lens labels are a **closed taxonomy**: only the canonical `audit::<lens>`
names are valid, and the filer refuses to emit a label the repository has never
created. Create them once with `audit-labels-bootstrap.js` before the first live
sweep — a generated label that does not exist makes every Issue create fail.

Do not invent per-finding labels. If you need another axis (a team, a
component), add it in triage on top of this set rather than teaching the sweep
to mint labels no taxonomy defines.

## Failure triage

| Symptom | Cause | Action |
| --- | --- | --- |
| Non-zero exit, `summary.reportFailures[]` populated | A lens report's tally is missing or disagrees with the parse | Re-run that lens; never downgrade with `--allow-missing-tally` |
| `[resolve-stories] ... carries no "agent::*" label` | An unenriched audit Story was named for delivery | Plan it (Step 5), or pass `--allow-unlabelled` deliberately |
| `[audit-to-stories] --severity "..." is not a severity` | A typo in the floor | Use one of the canonical levels |
| `duplicate-tally` in `summary.reportFailures[]` | The report declares the tally twice | Reword the prose copy; the Executive Summary line is the declaration |
| Same findings re-proposed every cycle | The filed Issues lack their `audit-fingerprints` footers, or dedup ran without the provider | File from the `--emit-stories` payloads verbatim; give dedup `gh` auth or `--issues-file` |
| `Unknown option` naming a `--ledger…` flag | A sweep script written before 2.70 | Drop the flag; there is no ledger to commit |
| `totals.create` far larger than the team can absorb | Severity floor too low for a first full-scope run | Raise `--severity` and re-dry-run |
